# Tick 194 - more-robust - backend-aware modeling route

## Axis

More robust / maturity methods + runner.

## Scope

Make `research modeling-plan` consume backend runtime evidence so route recommendations reflect what is actually available locally.

## Hypothesis

If `modeling-plan` accepts a `machine-status` artifact, it can avoid recommending missing backends as executable routes and can choose a bounded fallback for survey inference when appropriate.

## Intervention

Added backend evidence to `ModelingDecisionPlan`:

- `backendEvidence.source`
- available, missing, and not-checked backend ids
- warnings for missing backends
- candidate downgrading when a required backend is missing
- `--backend-status <machine-status.json>` CLI input
- complex-survey route fallback from `r-survey` to `python-linearized` when supplied evidence shows R survey unavailable but the local linearized runner is available
- stop-for-review when no survey-capable local backend is available

- CLI smoke: supplied a fake `machine-status.json` with `r-survey=missing` and `python-linearized=available`; `modeling-plan` routed to `paper-run --backend python-linearized`.

## Decision

Promote. Route selection is now tied to runtime evidence when available.

## Counter-Design Considered

I rejected making `modeling-plan` run backend probes itself by default. Probing can be slower and environment-dependent; accepting a `machine-status` artifact keeps planning deterministic and lets callers decide when to refresh runtime evidence.

## Remaining Doubt

ML adapters still use catalog availability rather than a supplied machine-status backend map for every optional Python package. This is acceptable for now because the ML registry already tracks optional package availability, but route planning should eventually merge both sources.

## Next Tick

Tick 195 is a remove/merge axis. It should reduce drift by making execution contracts or method-selection consumers use the same route/backend evidence instead of duplicating backend choice logic.
