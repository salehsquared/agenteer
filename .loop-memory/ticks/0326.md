# Tick 0326 - Route-Specific Trust-Layer QA Applicability

Axis: more-robust.
Contribution: `methods, QA, UX`.

## Hypothesis

If method QA applies route-specific diagnostic requirements, then diagnostic accuracy packets will surface only meaningful method warnings and reviewers will be less likely to ignore the trust layer.

## Scope

Respond directly to tick 0325. Harden existing method QA; do not add commands or alter domain repos.

## Intervention

Added route-family normalization for diagnostic accuracy, prevented diagnostic accuracy routes from inheriting regression-only collinearity/influence warnings, split sparse diagnostic cell wording from clinical coding concerns, and made the next action name sparse diagnostic stability when that is the dominant issue.

## Evidence

Before: the threshold diagnostic golden packet warned for missing collinearity, missing influence diagnostics, and vague semantic/coding concerns.

After manual smoke:

```json
{
  "readiness": "needs_methods_review",
  "warnings": [
    "Sparse diagnostic accuracy cells were detected; sensitivity, specificity, and predictive values may be unstable."
  ],
  "next": "Review sparse diagnostic cell stability, keep precision caveats visible, and consider exact intervals or threshold revision before promotion."
}
```

Regression tests now prove diagnostic routes treat collinearity/influence as not applicable while still recognizing diagnostic performance evidence.

## Decision

Promotion decision: `promote`. This directly resolves the tick 0325 challenge.

## Counter-Design Considered

Rejected changing collinearity/influence warnings to generic notes for every route. They are still important for regression-like routes; the fix is route applicability, not global softening.
