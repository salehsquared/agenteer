# Tick 193 - faster/simpler - stats-run lifecycle visibility

## Axis

Faster/simpler / maturity UX + truth.

## Scope

Make standard-table `stats-run` evidence visible in the existing reviewer lifecycle surface without adding a new CLI command.

## Hypothesis

If `paper-lifecycle` can see `stats-run.json`, the standard-table statistics path is less likely to become an invisible execution island. A stats-backed packet should expose stats status, method, binding, and typed issue codes in the same reviewer-facing lifecycle view used by generated papers.

## Intervention

Added `statsRun` to `ResearchPaperLifecycle`:

- reads packet-local `stats-run.json`
- reports `succeeded | failed | missing`
- reports method, binding status, issue codes, and path
- blocks lifecycle when `stats-run` failed
- renders the stats state in human output and JSON

## Decision

Promote. This makes the stats path visible to the same reviewer-facing lifecycle surface as paper-run.

## Counter-Design Considered

I rejected creating a new `stats-lifecycle` command. That would worsen the analysis surface maze called out in Tick 191. The lifecycle view should absorb runner-family evidence where possible.
