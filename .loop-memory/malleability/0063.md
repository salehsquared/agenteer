# Tick 0063 Capability Rave

## Ten Fast-Malleable Items

- `listResearchArtifactNames`: can be generated from stage metadata plus extra packet artifacts.
- `RESEARCH_STAGE_ARTIFACTS`: can include category tags such as primary, audit, optional.
- `packet-readiness` renderer: can group stop/action fields before component detail.
- `recommendedCommands`: can split shell chains into individual commands.
- `docs/research-pipeline.md`: can generate command groups from metadata.
- `qa-dashboard`: can reuse readiness components for shared statuses.
- `packet-summary`: can show decision posture if `packet-readiness.json` exists.
- `ResearchPacketReadinessComponent`: can include severity rank.
- `manifest-verify`: can report stage category when hashes drift.
- `stage-artifacts`: can expose owner command for each artifact.

## Ten Looks-Fixed-But-Is-Not Items

- The artifact allowlist looks fixed but can be derived.
- The docs command lists look handwritten but can be generated or grouped.
- Exit codes look per-command but can be policy-driven by posture.
- Human readiness output looks final but can be reordered without schema change.
- QA dashboard and readiness look separate but can share component adapters.
- Stage artifacts look file-only but can carry producing command and consumer command.
- Export looks a packaging step but can become a reproducibility policy gate.
- Report review looks text-only but can consume claim-guard output.
- Stop reasons look user-facing but can feed repair planning.
- Open questions look passive but can generate tick candidates.

## Gaps That Should Be Malleable But Are Not

- No central artifact category taxonomy: primary, audit, derived, optional.
- No generated docs from command metadata.
- No shared component construction between QA and readiness.

## Picked Item

Scheduled a remove/merge target: derive the artifact allowlist from `RESEARCH_STAGE_ARTIFACTS` plus a small explicit extra-artifacts list. This would reduce drift introduced by hand-maintaining two artifact registries.
