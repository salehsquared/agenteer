# Tick 0071 Challenge: A Competing Tool Would Make Profiles First-Class

Persona: Author of competing tool

## Critique

If I were building against Agenteer, I would not want to patch one readiness command every time a new domain appears. I would make the readiness profile a first-class object with profile id, scope, references, limitations, component policy, and posture policy. The current command is still a hardcoded implementation of one implicit profile.

The practical critique is that docs alone may not be enough. Without a field in the output, downstream packets cannot say which readiness profile was used.

## Actionable Implications

- Add a `readinessProfile` object when feasible: id, label, domain, and caveat.
- Keep it minimal and backward-compatible.
- Do not implement profile selection yet; start by naming the default profile.

## Evidence That Would Change This Critique

I would soften the critique if readiness output included a profile id such as `observational-survey-v1`, even if profile selection is future work.

## Recommended Next Tick

Add a minimal `readinessProfile` object to `packet-readiness` and document that profile selection is not implemented yet.
