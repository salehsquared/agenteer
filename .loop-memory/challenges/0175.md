# Tick 175 Challenge - Methodology Archivist

## Critique

The current `paper-run` packets are reviewable, but not yet archive-stable. A future reviewer can inspect analysis, paper, QA, runner record, task receipts, and lifecycle, but there is no single repeatability artifact saying: "I reran the same AnalysisSpec and these scientifically relevant fields were unchanged within tolerance."

This matters because generated papers are not static prose; they are the visible end of a computation. If a later dependency, local cache, or runner edit changes the effect estimate, row count, weight domain, or QA result, the archive needs to show whether that change is expected, benign, or a blocker.

The current golden manifest system already has rerun-diff ideas, but fresh `paper-run` packets do not automatically connect to a paper-level repeat check. The risk is bifurcation: mature golden packets get reproducibility treatment, while new real papers only get one successful lifecycle.

## Actionable Implications

- Add a repeatability check for `paper-run` packet outputs that compares scientific fields, not raw Markdown bytes.
- Compare at least: complete-case N, effect estimate, SE, CI, p value, model type, weight variable, weight domain, QA status, and lifecycle status.
- Treat changed input file hashes or AnalysisSpec hash as a hard invalidation, not an ordinary numeric drift.
- Write a `rerun-stability.json` artifact that can be included in lifecycle/manifest later.

## Evidence That Would Change This Critique

- A fresh `paper-run` packet with a repeatability artifact generated from a second run.
- A deterministic test showing that numeric drift beyond tolerance becomes a blocker.
- Lifecycle or manifest output surfacing repeatability status without requiring manual JSON comparison.
