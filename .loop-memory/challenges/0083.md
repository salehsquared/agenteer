# Tick 0083 Challenge

Persona: Framework minimalist

## Critique

The real-data work is valuable, but Agenteer is close to adding three overlapping concepts for one need: `table-summary`, `data-access`, and `real-runner-spec`. The user sees these as separate commands, but the workflow question is simpler: "Can this packet safely and reproducibly read this dataset through this adapter?"

Right now, `table-summary` contains file and runtime provenance, `data-access` declares files, and `real-runner-spec` declares execution. That division is defensible internally, but the CLI can become tedious if every real-data packet needs separate summary, access, runner, variable-map, readiness, and scout commands before anything substantive happens.

The danger is a research pipeline that is inspectable but chore-heavy. The user does not care about the exact sequence of scaffolding commands. They care that the packet records enough to reproduce the analysis and that failures point to the missing piece.

## Actionable Implications

- Do not add more real-data commands until `data-access` can absorb table-summary provenance.
- Prefer one packet-level `real-data-adapter.json` or enriched `data-access.json` over more top-level artifacts.
- Make `real-study-readiness` read the unified artifact instead of requiring users to mentally join command outputs.
- Consider deprecating `real-runner-spec` once the adapter artifact can declare execution mode, required variables, safety, and runtime.
- Keep `table-summary` as a low-level inspection command, not a required user-facing stage.

## Evidence That Would Change This Critique

- A single command can create or update the packet's real-data adapter evidence from actual Parquet.
- Readiness reports can explain real-data status from one artifact.
- The command list gets shorter, not longer, after adding real-data support.
