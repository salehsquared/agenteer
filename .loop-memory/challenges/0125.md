# Tick 0125 Challenge

Persona: Reliability engineer.

Critique: the paper corpus now looks organized, but every paper still depends on approximate weighted regression and manually authored analysis scripts. The reliability risk is no longer "can we produce a paper?" It is "can we prove the paper was generated by a repeatable runner contract rather than by bespoke one-off code?" The index and QA make outputs inspectable, but they do not yet record a runner command, input file hashes for each paper, dependency versions, or a reproducible execution script inside each paper directory.

Actionable implications:

- Each paper directory should include a `run.json` or `runner-record.json` with command, runtime, input Parquet paths or hashes, generated files, and status.
- The paper index should eventually surface runner status, not only QA status.
- A future paper should be generated through a reusable runner primitive or template, not a one-off heredoc.
- Until full complex survey variance exists, the runner record should make the approximate variance method impossible to miss.

What would change this critique: a paper generated by a reusable local runner that writes analysis, paper, critique, QA, and runner provenance in one reproducible directory.
