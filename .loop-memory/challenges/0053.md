# Tick 0053 Challenge: Readiness Is Becoming A Second Checkpoint System

Persona: Reliability engineer

## Critique

The new `packet-readiness` command is useful, but it now reinterprets many of the same stage artifacts that `checkpoint`, `next`, `qa-dashboard`, `packet-summary`, and `stage-artifacts` already touch. That creates drift risk: one command can say a packet is complete while another says a component is missing or blocked.

The reliability problem is not the number of checks. It is the absence of a single shared dependency description for each high-level projection. `packet-readiness` has bespoke component logic; `qa-dashboard` has separate bespoke check logic; `checkpoint` has its own artifact inference. Every new command increases the chance that artifact names, required/optional status, and severity mappings diverge again.

## Actionable Implications

- Next code tick should reduce drift, not add another user-facing command.
- Centralize readiness component construction or let `qa-dashboard` and `packet-readiness` share a small component adapter.
- Add a regression that catches provenance filename drift across `stage-artifacts`, `qa-dashboard`, and `packet-readiness`.
- Avoid making `stage-artifacts` the "source of truth" unless all projections consume it.

## Evidence That Would Change This Critique

I would soften the critique if stage artifact names and readiness component statuses were derived from one shared registry or adapter, and if a test proved provenance was consistently named across all projections.

## Recommended Next Tick

Do a remove-or-merge style implementation: extract shared readiness/QA component mapping or at minimum add cross-projection drift coverage for provenance.
