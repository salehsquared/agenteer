# Tick 0155 Challenge: Adversarial Security Reviewer

## Critique

The golden packet is now strong for local review, but it is also becoming increasingly dangerous to accidentally export. The manifest now tracks 15 artifacts, many of which intentionally preserve absolute local paths into `/Users/saleh/...` and MedBrevia's local NHANES cache. That is acceptable for local reproducibility, but it creates an attractive nuisance: a valid manifest can be mistaken for a shareable package.

The current `shareStatus` says the packet is blocked for sharing, and `share-safety.json` exists, but the verifier treats share safety as a check value rather than a hard export boundary. A future export command or human reviewer could still copy the packet and call it "verified." Verification should keep saying "valid for local review," not "valid" in a context-free way.

The second risk is path exfiltration through derived receipts. The local review note is safe, but runner records, manifests, verification receipts, repair plans, and README references can preserve absolute local paths. If the system later adds a redacted export, it needs an allowlist of shareable roles, not a denylist of path-looking strings.

## Actionable Implications

1. Add a manifest verification field or human output distinction: `validLocal: true`, `validForShare: false`.
2. Add a manifest role policy: `local-review`, `local-provenance`, `shareable-redacted`, `repair`, `verification`.
3. Make export/share routines copy only shareable-redacted roles by default.
4. Keep local manifest verification valid, but impossible to misread as external-share validation.

## Evidence That Would Change This Critique

- Manifest verification output that explicitly separates local validity from share validity.
- A redacted export receipt proving no absolute paths in shareable artifacts.
- A role-based export policy test.
