# Tick 0089 Challenge

Persona: New contributor

## Critique

`real-study-readiness` is mixing two different readiness stories:

1. Synthetic fixture readiness: useful for testing the pipeline locally.
2. Real local data readiness: useful for running against actual curated datasets.

The current output calls `runner-spec.json` "useful", but the status model treats it as a missing blocker. That is confusing. A new contributor will either cargo-cult `runner-spec.json` into every real-data packet or assume the packet is broken even though all real-data evidence passes.

The command should separate blocking requirements from advisory checks. This is especially important because the research pipeline will keep adding more preflight checks. If every useful artifact becomes a hard readiness requirement, the CLI will permanently say `not_ready`.

## Actionable Implications

- Add requirement severity or blocking semantics to `ResearchRealStudyReadiness`.
- Make `fixture-runner-spec` advisory for real-data readiness.
- Compute `ready_for_local_real_data` from blocking requirements only.
- Render advisory requirements distinctly.
- Keep the old requirement visible so synthetic fixture discipline is not lost.

## Evidence That Would Change This Critique

- The two-domain actual NHANES packet reports `ready_for_local_real_data` while still noting missing fixture-runner evidence.
- Tests prove advisory requirements do not affect readiness status.
- Human output clearly distinguishes "blocking" from "recommended".
