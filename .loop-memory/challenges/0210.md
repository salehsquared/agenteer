# Challenge 0210 - ML Comparison Still Lacks Model-Card Evidence

Persona: clinical ML reviewer.

## Web-Creativity Inputs

- Model Cards for Model Reporting argues for standardized model documentation including intended use and performance across relevant groups: https://arxiv.org/abs/1810.03993
- TRIPOD+AI updates reporting guidance for prediction models using regression or ML and emphasizes transparent model development/evaluation reporting: https://www.bmj.com/content/385/bmj-2023-078378
- DECIDE-AI focuses early-stage clinical AI evaluation and makes clear that reporting must include context, user interaction, and implementation setting, not only model metrics: https://www.nature.com/articles/s41591-022-01772-9

## Critique

`comparisonPosture=baseline_comparison_ready` is a useful gate, but it is still a metrics-first safety case. It asks whether two models succeeded, whether a baseline exists, and whether binary calibration artifacts exist. It does not yet ask the model-card questions that matter before a prediction result becomes a research product:

- intended use and intended non-use
- target population and exclusion boundaries
- subgroup performance or explicit absence of subgroup evidence
- data leakage review
- calibration interpretation and limitations
- deployment/prospective-evaluation boundary
- model family transparency tradeoff

The current posture can say "baseline ready" even when the only evidence is aggregate accuracy/AUROC. That is not enough for medical/public-health prediction research.

## Required Next Response

Do not add more estimators. Add a model-card-style `ml-review-card` or comparison manifest that summarizes intended use, non-use, metrics, calibration, subgroup evidence status, leakage warnings, and next validation boundary from existing `ml-compare` and runs.

Best next implementation: create `research ml-review-card --comparison <comparison.json> --out <card.md|json>`, or if avoiding a new command, make `ml-compare` emit `model-review-card.md` alongside `comparison.json`.

## Tail-End Idea

Prediction models should have a "claim firewall": every downstream claim must cite a model-card field, not just a metric. If the field is absent, the claim cannot be generated.
