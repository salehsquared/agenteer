# Tick 191 Challenge - Framework Minimalist

## Critique

The research machine now has too many neighboring commands for a user or agent to confidently choose the right path:

- `modeling-plan`
- `method-select`
- `method-apply`
- `execution-contract`
- `stats-run`
- `ml-run`
- `paper-run`
- `paper-lifecycle`

Each command is defensible alone. Together, they form a decision maze. The danger is that the orchestrating LLM keeps knowing the intended route because it built the pieces, while a future agent or user cannot infer the golden path.

The surface also mixes abstraction levels. `modeling-plan` is strategic, `method-select` is ontology selection, `stats-run` is raw execution, and `paper-run` is composed packet generation. A mature framework should make one recommended path obvious and demote the rest to building blocks.

## Actionable Implications

- Add a single "analysis front door" projection that says: for this question/data/spec, use `paper-run`, `stats-run`, `ml-run`, or stop for review.
- Do not add another runner before this route is clear.
- Split docs into "golden path" and "building blocks."
- Make `modeling-plan.nextAction` more concrete: not just promote a candidate, but "run this exact next command" or "create these missing artifacts first."
- Consider demoting `method-select` from user-facing docs once `modeling-plan` embeds method-selection evidence.

## Evidence That Would Change This Critique

- A new user can go from question plus CSV to a correct stats packet using one documented sequence.
- CLI help points to one path for standard tables, one path for survey papers, and one path for ML prediction.
- Lifecycle can summarize packets produced by all runner families.
