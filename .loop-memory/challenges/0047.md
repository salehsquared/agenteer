# Tick 0047 Challenge: Research Readiness Is Not Validity

Persona: Skeptical statistician

## Critique

The proposed `research-readiness` layer is directionally right, but it can easily become another misleading stamp. A packet can have valid hashes, methods-validation artifacts, report review, and a provenance graph while still being a weak or misleading study.

The core risk is conflating four different questions:

1. Did the files change unexpectedly?
2. Did the pipeline run the expected stages?
3. Are the statistical assumptions appropriate for the data and design?
4. Are the report claims warranted by the analysis?

The current integrity layer answers mostly question 1. A readiness layer should answer questions 2-4 only as scoped checks, not as a single "ready" declaration.

## Actionable Implications

- `research-readiness` should report `mode` and `scope`, just like `packet-verify`.
- It should produce component statuses rather than a broad pass/fail stamp.
- It should include explicit limitations for survey/cross-sectional data: weights, missingness, subsample eligibility, sparse cells, and causal limits.
- It should treat missing methods validation, report review, claim guard, and provenance as separate issues.
- It should avoid saying "valid study" or "research ready" without qualifiers.

## Evidence That Would Change This Critique

I would soften the critique if the readiness layer clearly separates:

- integrity readiness
- workflow completeness
- methods defensibility
- claim support
- reproducibility/export readiness

and if the CLI output uses language like "ready for review" or "available checks passed" rather than "valid."

## Recommended Next Tick

Add a minimal `research packet-readiness --packet <dir> [--json]` command that composes existing artifacts and reports component statuses. Do not make it enforce or certify scientific validity.
