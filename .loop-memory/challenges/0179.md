# Tick 179 Challenge - Modeling Plan Truth Pressure

The new `research modeling-plan` command is directionally useful, but it is not yet strong enough to trust as the controller for serious medical/public-health modeling.

## Findings

1. It still depends too much on user-provided flags. If the user forgets `--survey`, `--high-missingness`, `--small-sample`, or `--predict`, the plan can recommend a plausible but wrong path. The planner should ingest table summaries, AnalysisSpec evidence, and backend status before ranking.

2. It ranks workflow policy as a "primary" candidate in some cases. That is defensible as a stop gate, but inconvenient as a model plan. The output should probably separate `blockingPolicies` from executable model candidates so the human sees both the guardrail and the run path.

3. The ML choices are shallowly data-aware. Logistic regression, random forest, and gradient boosting are ranked without using row count, feature count, class balance, categorical cardinality, missingness, or leakage risk. This risks giving the same answer for a 90-row sparse table and a 90,000-row clean table.

4. Statistical and ML candidates are not yet unified around an estimand. A predictive task should rank by validation metrics and calibration; an explanatory task should rank by effect measure, variance estimator, survey design, and confounding disclosure. The plan currently mixes both in a single candidate list.

5. Optional dependency behavior is safe but not strategic. XGBoost/LightGBM/CatBoost are listed as unavailable, but the planner does not say whether installing them would materially improve a task or just add complexity.

6. Survival, text, image, graph, time-series, geospatial, and causal-ML areas are correctly treated as future adapters, but the plan does not yet give a concrete "next artifact" for those domains beyond stop-for-review.

7. There is no feedback loop from actual run outcomes. A model that fails calibration, has unstable rerun metrics, or performs worse than a baseline should influence later planning.

## Required Response

Tick 180 should not add more model names. It should make the decision layer evidence-aware:

- accept a `tableSummary` or table file and derive row count, feature count, missingness, likely class count, and small-sample flags
- split `blockingPolicies` from executable candidates
- require calibration metrics for binary clinical prediction candidates
- downgrade high-capacity ML models for small or high-missingness tables
- emit concrete next artifacts for unsupported domains
- add tests showing the same question produces different recommendations for low-N/high-missingness versus large/clean data

## Counter-Design Rejected

I reject adding more adapters before fixing selection quality. More model families will make the system look broader while increasing the chance that the planner picks an inappropriate analysis for the data shape.
