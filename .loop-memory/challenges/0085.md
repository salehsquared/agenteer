# Tick 0085 Challenge

Persona: End-user clinician

## Critique

The provenance direction is technically sound, but it risks burying the clinical decision under metadata. A clinician or research user does not want to inspect entity/activity/agent terminology. They need to know whether the data used for the analysis are the intended data, whether the right rows and variables were available, and what limitations affect interpretation.

The current real-data outputs still emphasize engineering evidence: file hashes, package versions, adapter names, and rows/columns. Those are necessary for reproducibility, but they are not sufficient for trust. The evidence artifact should also summarize clinical/research relevance:

- Which dataset/release was used?
- Which domains/tables were actually read?
- Are the key endpoint/exposure/covariate variables present?
- Are there missingness or sparse-cell issues that change the interpretation?
- Is the analysis still only feasibility/mapping, or has it reached interpretable results?

If `data-access.json` absorbs table-summary provenance, it must not become an opaque machine artifact. It should include a short human `decisionSummary` or `clinicalSummary` that states what the file evidence means.

## Actionable Implications

- Add human-readable summary fields when enriching `data-access.json`.
- Separate reproducibility evidence from clinical/research readiness.
- Keep file hash visible but not central in the human output.
- Make real-data readiness explain "ready for mapping", "ready for scout", or "ready for execution", not just pass/fail.

## Evidence That Would Change This Critique

- A real-data readiness command can explain the NHANES diabetes Parquet status in one paragraph.
- A non-engineer can identify from the artifact whether HbA1c and diabetes variables were found and whether missingness matters.
- The packet keeps hashes/package versions for audit while surfacing clinical implications first.
