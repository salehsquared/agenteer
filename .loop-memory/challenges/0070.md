# Tick 0070 Challenge: Readiness May Not Scale Across Domains Yet

Persona: Scaling skeptic

## Critique

The current readiness model is improving for NHANES-like observational packets, but its components are still biased toward this first dogfood domain. `claim-guard`, STROBE references, survey caveats, and local fixture assumptions are appropriate here, but a future genomics, imaging, trial, EHR, qualitative, or operations dataset may need different review posture logic.

The risk is overfitting Agenteer's general research pipeline to the first medical analytics substrate. A strong framework should make domain-specific readiness modules explicit rather than quietly embedding them in one command.

## Actionable Implications

- Add a future `readinessProfile` concept, but do not implement it until another domain stresses the pipeline.
- For now, label the current readiness limitations as observational/survey oriented.
- Keep `references` extensible and avoid treating STROBE as the only framework.
- Do not call the command general medical validity readiness.

## Evidence That Would Change This Critique

I would soften the critique if readiness output named its profile or if the docs clearly said the current references/limitations are observational-survey defaults.

## Recommended Next Tick

Add docs language that `packet-readiness` currently uses an observational/survey-oriented default profile and is expected to grow domain-specific profiles later.
