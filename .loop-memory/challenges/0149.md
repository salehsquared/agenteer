# Tick 0149 Challenge: Reliability Engineer

## Critique

The new AnalysisSpec policy and repair classification are directionally correct, but they are not yet wired into the live golden packet's operational path. The code has tests showing that an approximate-inference paper-QA failure can stop executable repair. The golden packet, however, does not yet have a root-level `paper-qa.json` or `repair-plan.json` that demonstrates this behavior against the canonical artifact set.

This is a reliability smell: the framework can now express a failure mode, but the main dogfood packet does not prove the full path from policy to QA to repair stop. It would be easy for future changes to keep the unit tests passing while the golden packet drifts back into "paper directory plus manifest" shape.

The second issue is provenance. The runner record says what ran, and the AnalysisSpec says what should run, but the runner record is not yet a spec-first execution receipt. If the spec changes, it is unclear whether the runner record is stale unless a reviewer manually compares hashes.

## Actionable Implications

1. Add a local golden `repair-plan.json` produced from current artifacts, even if it reports no repair needed or only share/export blockers.
2. Add root-level golden QA/provenance aliases or manifest roles so the packet can be reviewed without jumping into the paper corpus directory.
3. Make runner records cite the current AnalysisSpec hash and fail verification if stale.
4. Add a smoke test that composes AnalysisSpec policy, paper QA, repair-plan classification, and manifest verification.

## Evidence That Would Change This Critique

- A live golden repair plan generated from current packet artifacts.
- A runner receipt with an AnalysisSpec hash matching the current `analysis-spec.json`.
- A test where changing the spec hash makes runner/golden verification fail.
