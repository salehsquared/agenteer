# Tick 0059 Challenge: New Contributors Cannot Tell Which Readiness Fields Are Stable

Persona: New contributor

## Critique

`packet-readiness` now has useful fields, but their intended stability is unclear. A contributor sees `status`, `decisionPosture`, `sharePosture`, `stopReasons`, `recommendedCommands`, `summary`, `clinicianSummary`, `components`, `limitations`, `references`, and `packetVerification`. Some are API contracts, some are human wording, and some are derived convenience fields.

Without schema guidance, contributors may change text fields that scripts rely on, or rely on fields meant only for humans. This is the kind of accidental coupling that makes CLI JSON hard to evolve.

## Actionable Implications

- Document which readiness fields are script-stable.
- Add a schema version or explicit contract note for packet-readiness JSON.
- Prefer scripts to use `status`, `decisionPosture`, `sharePosture`, component IDs/statuses, and `recommendedCommands`.
- Treat `summary`, `clinicianSummary`, and component detail text as human-facing and changeable.

## Evidence That Would Change This Critique

I would soften the critique if docs or output marked stable fields clearly enough that a new contributor could extend the command without guessing.

## Recommended Next Tick

Add a small `docs/research-pipeline.md` subsection for packet-readiness JSON contract stability, or add `contractVersion` to the readiness object.
