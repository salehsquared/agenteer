# Challenge 0205 - Bounded Route Can Normalize Unbound Statistics

Persona: methods-safety reviewer.

## Critique

`research analysis-run` removes sequencing friction, but it currently also makes it easy to run an unbound standard-table analysis and receive a polished bundle with `modeling-plan`, `stats-run`, `analysis-manifest`, and post-run planning. The manifest does say `exploratory_only`, and post-run planning routes to method/spec binding, but the command still feels like a complete run to a hurried user.

The problem is not the command existing. The problem is default posture. If the user asks for a research pipeline, the first-class route should either:

1. require method-selection/AnalysisSpec binding before execution, or
2. force the output directory and command text to scream exploratory, or
3. expose a strict flag such as `--require-bound` that blocks unbound runs for benchmark/paper-like use.

Right now `analysis-run` is honest in artifacts but permissive in ergonomics.

## Failure Mode

A future agent may run `analysis-run`, see a successful stats run and complete manifest, then move on without responding to `rerun-with-binding`. That recreates the manual-work problem: execution success masquerades as research readiness.

## Required Next Response

Add a policy gate to `analysis-run`:

- default can remain exploratory for fast local development, but the command must surface this loudly; and
- `--require-bound` should fail if no method-selection or AnalysisSpec evidence is provided; or
- `analysis-run` should accept `--method-selection` / `--analysis-spec` and pass them into `stats-run`, making bound runs possible through the composed route.

Best next implementation: add `--method-selection`, `--analysis-spec`, and `--require-bound` to `analysis-run`, then test that unbound strict mode fails and bound mode produces `bound_standard_table` readiness.
