# Challenge 0195 - New Contributor - stats path is still too implicit

## Persona

New contributor.

## Critique

The last two ticks made `stats-run` easier to route to and visible in lifecycle, but a new contributor would still not know how to turn a standard-table method into a complete packet. The current path is still:

1. infer route with `modeling-plan`
2. run `stats-run`
3. manually surround `stats-run.json` with paper/report/QA/task artifacts if lifecycle should pass

That means `stats-run` has improved as a computation primitive but not yet as a research-product primitive.

There is also a concrete implementation smell in the Python bridge: it prints `json.dumps(run(req))` twice in the success path. The current tests pass because stdout parsing apparently tolerates the first JSON object in practice or the observed branch did not break, but duplicate JSON output is fragile and should be removed before adding more methods.

## Actionable Implications

- Fix the duplicate Python bridge success print before expanding method breadth.
- Make `stats-run` generate a minimal packet-grade report/QA artifact or add a narrowly scoped packet wrapper that consumes `StatsRunResult`.
- Define what a standard-table stats packet must contain: `stats-run.json`, `estimates.csv`, `diagnostics.json`, method-selection binding, report/interpretation boundary, lifecycle summary, and optional task envelope.
- Do not add more statistical methods until the stats path has a complete reviewer-facing artifact path.

## Evidence That Would Change This Critique

- A fresh standard-table question can go from `modeling-plan` to runnable stats execution to lifecycle-ready packet with no hand-authored shell artifacts.
- The stats runner emits exactly one JSON result on stdout in all success/failure paths.
- Lifecycle can distinguish `stats-run succeeded but unbound`, `stats-run exploratory`, and `stats-run locally review-ready`.

## Priority

High. This is an execution/product boundary issue, not a cosmetic issue.
